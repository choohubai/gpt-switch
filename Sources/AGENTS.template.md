请遵循以下全局工作方式：

## 一、任务开始前：读取基线

1. 每次任务开始前，先完整读取从项目根目录到当前工作目录适用的 `AGENTS.md`，再完整读取项目专属规划文档（如有），并将其作为产品和功能实施基线。
2. 完成两份基线的读取和核对前，不得修改任何代码、配置、Schema、迁移、依赖、样式、测试、构建、部署或文档，也不得先实施后补读。
3. 开工前必须明确本次任务对应的规划文档章节、实施阶段和验收条目；无法对应的任务必须先获得项目负责人确认，不得直接开工。
4. **先确认逻辑再动代码**：任何改动前都必须先完成改动逻辑自检——确认当前现象与根因、预期行为、调用链、影响范围、边界条件和现有测试，确认拟议改动能覆盖根因且不破坏既有行为；同时检查当前状态、相关文件、调用方、测试和现有模式；不得先改再靠运行结果判断逻辑对不对，自检未通过不得开始改动。
5. **工作区出现别人的在制品时一律不动**：发现工作区里有不是本次任务产生的未提交改动（用户或其他会话正在改），不得 `git stash`、`git checkout`、`git restore`、`git revert`，也不得把它们提交、推送或发布；立即告知用户并等其决定。需要干净工作区才能做的事（例如本地发布构建）同样先问，不得自行把别人的改动藏起来再继续。
6. 本文件的约束同时适用于实现类任务和审查、评审、复核、给结论类任务；不得以“只是审查”“只是看看”为由跳过任何一条。审查任务同样必须先完成基线读取、复用检查证据和文档自洽检查，再输出结论。

### 需求澄清与决策边界（防猜测、防过度思考）

- **先查事实，再问决策**：能通过相关代码、调用方、测试和文档查清的问题，先自行核实；需要用户确定的业务规则、字段含义和数据口径，不得自行推断。
- **有实质歧义，先澄清再修改**：需求与现有逻辑、字段语义、数据口径或约定不一致，且用户未明确要求改变该约定；或存在会改变业务结果、接口契约、数据处理或验收标准的多种解释时，必须先澄清。不得默选一种解释硬写，也不得默认现有实现一定正确。
- **澄清保持简短**：按“现状是什么 → 分歧或不确定点在哪 → 可选走法及关键影响 → 推荐哪种、请用户确认”的顺序说明。只问影响当前决策的问题，不先写长篇分析，不为凑选项展开无关方案。
- **发现决策缺口就及时问**：明确说“这里我不确定，需要确认 X”。不得反复搜索或空想来替用户决定业务规则；关键口径确认前，不实施依赖该口径的修改，可以继续不受影响的只读核查。
- **常规技术选择自行决定**：不影响业务含义和对外行为的实现细节，优先沿用现有模式，自行选择最小可行方案，不要把常规技术选择交给用户。用户已明确的决定不得重复询问，除非发现新的冲突或风险。

### 文档自洽检查（实现前、审查前、给结论前强制）

凡以设计文档、规划文档或需求文档作为实现、审查或验收基准的任务，在动手实现、开始审查或给出结论之前，必须先对该文档做自洽检查并输出检查结论；检查不通过时停止，先澄清或修订文档，不得进入实现或审查。

检查至少覆盖：

1. 边界声明与入口设计是否一致：谁是谁的聚合根或子实体、谁有权写、写入口在哪；
2. 例外路径是否被显式标注为待确认，而不是当成既定设计继续沿用；
3. 每条不变式是否有明确守护者，是否被同一文档的例外推翻；
4. 锁顺序、事务边界、并发约定是否覆盖文档中出现的所有主体；
5. 文档声明的契约或能力，是否在交付物或后续阶段中有承接方。

判定基准是用户要求和领域规则，不是文档本身；不得以“代码与文档一致”证明文档正确。检查不通过时，必须逐条列出冲突位置与冲突双方，不得用“已落地”“已对齐”等表述收尾。

### 阶段归属与交付方检查（动手前、审查前强制）

1. 动手前先对照规划文档的阶段划分与交付方，写明本次任务属于哪个阶段、由哪一方交付；归属不清或跨越阶段时先澄清，不得先实施后解释。
2. 审查、评审类任务的第一项检查是阶段与职责归属：确认既有或拟议实现是否落在当前阶段、当前交付方范围内；越界项单独列出，并写明应归属的阶段或交付方。
3. 文档是实现与审查的基准：实现与文档冲突时改实现或先澄清，不得用实现反推文档；确需修订文档时，依据必须是用户要求或领域规则，不能是“代码已经这么写了”。

## 二、实现原则

#### 2.1 创建前先检索并复用

> **这是最高优先级约束：不得放着已有能力不用，另写一套实现。**

在创建任何新的文件、组件、页面、服务、工具函数、Store、Composable、中间件、Provider、API 接口、数据模型、配置模块或测试文件之前，**必须先搜索项目代码库，确认是否已有可复用或可扩展的实现**。搜索范围必须覆盖：

- **前端**：公共组件、组合式函数、状态管理、工具函数、API 封装、页面、路由、样式、类型、常量、国际化、静态资源
- **后端**：请求入口、业务逻辑、数据访问、数据模型、中间件、工具函数、配置、迁移、类型、常量、公共包、渠道提供者、外部适配器

检索不能只看同名符号，还要按职责搜索。例如需要“发送通知”时，应检查 `notify`、`sendMessage`、`push`、`alert` 等可能承担同一职责的实现。

发现相同或近似功能时必须主动复用，禁止复制现有代码后改名，禁止新建平行的服务、接口、组件、页面、状态管理、工具函数或基础设施来实现同一职责。不只是同名搜索，还要按职责搜索：要的是“发送通知”的能力，不管它叫 `notify`、`sendMessage`、`push` 还是 `alert`，只要干了这件事就复用。

在首次修改任何代码、配置、Schema、迁移或测试前，必须先在对话中明确给出以下复用检查证据：

1. 本次任务对应的规划文档章节、实施阶段和验收条目；
2. 按职责搜索到的现有实现、调用方和相关测试；
3. 本次决定复用或扩展的现有实现；
4. 确需新增时，现有实现无法满足需求的具体原因。

以上内容未给出、证据不完整或仍存在未核实项时，不得开始修改；修改后的补查不能替代修改前检查。对 `Clock`、ID 生成器、错误码、Mapper、索引、事务和状态模型等基础能力必须进行全仓库职责搜索，不得只检查当前文件、当前模块或同名类型。

**文档草图不构成新增依据**：设计文档、需求文档和字段草图中的字段名、枚举名、错误码只是示意，不得直接照抄成新的表列、枚举、错误码或常量。新增这些标识前，必须先在仓库中按职责确认既有对应物（如审计列 `created_at`/`updated_at`、软删除列 `deleted_at`、既有状态枚举、既有错误码等）；能复用或扩展现有实现时，一律不得另造同义字段或同义类型，确需新增时仍按本节要求给出证据与理由。

#### 2.2 扩展优先于新建

现有能力不能完全满足需求时，应在原有归属模块和架构边界内**扩展**接口、配置、参数、组合方式或实现，不得绕开原实现另建平行链路。

**前端扩展方式：**

- 在现有组件上增加 `props`、`slots`、`events` 或变体
- 在现有函数上增加可选参数或配置项
- 在现有 Store 上增加 `state` / `getter` / `action`
- 在现有 API 模块上增加新的请求方法

**后端扩展方式：**

- 在现有 Service 上增加新的方法，而非新建 Service
- 在现有 Handler 上增加新的路由或参数
- 在现有 Repository 上增加新的查询方法
- 在现有 Middleware 上增加新的校验逻辑
- 在现有 Provider / Adapter 上增加新的渠道实现
- 在现有数据模型上增加字段，而非新建平行模型

#### 2.3 允许新增实现的条件

只有同时满足以下全部条件时，才允许新增文件或实现：

1. 已搜索并确认仓库中不存在相同职责的实现。
2. 现有抽象无法通过合理扩展满足需求。
3. 新增实现符合项目既有架构和分层约定。

完成后必须在提交信息或变更记录中写明：**检索范围、复用结论、新增理由**。

#### 2.4 沿用现有标识机制

新增数据库主键、业务编号、订单号、Slug、幂等键、请求 ID 或其他唯一标识时，必须沿用现有类型、生成器、格式和生命周期约定，禁止另写一套标识生成逻辑。

#### 2.5 最小变更

> 来源：cursorrules `codequality.mdc`、`javascript-typescript-code-quality-cursorrules-pro.mdc`

1. **只修改与任务直接相关的代码**，不做无关的重构、重命名、格式化或依赖升级，不要顺手改、顺手删或顺手重构无关代码。
2. **保持现有代码结构**，不删除、不移动、不重命名与任务无关的代码和注释。
3. **不要发明变更**，只做任务明确要求的事，不要主动添加认为“更好”的额外功能。
4. **代码变更 = 潜在 Bug + 技术债务**，用最少的代码变更完成任务目标。
5. 不要建议或执行仅涉及空格、换行、格式调整的变更。

#### 2.6 反过度工程

> 来源：cursorrules `anti-overengineering.mdc`

1. **最简单的方案优先**，不要为了“可扩展”引入当前没有实际需求的抽象、接口、工厂或配置层。
2. **只有一个实现时，抽象就是债务**，等到第二个实现出现时再提取共同接口。
3. **不要引入不必要的依赖**，新增第三方库前先确认现有依赖是否已覆盖该能力。
4. **不要对小改动重写整个文件**，优先使用编辑工具做精准修改。
5. **只实现当前已确认的功能**：字段、索引、接口、抽象、配置、兼容逻辑和扩展点必须服务于当前规划文档、验收条目或真实调用方；禁止为未经确认的未来需求预留实现。后续出现明确需求时，再根据实际调用方扩展现有实现。
6. **禁止无实际失败路径的防御性判断**：新增判空、状态、归属或结果校验前，必须确认上游类型、当前查询条件和数据库约束是否已经保证该条件；已经保证时不得在调用层重复判断。外部输入、权限或租户边界、无法由下层约束保证的业务状态、并发写入结果等存在真实失败路径的校验必须保留，并由对应测试覆盖。
7. 交付前自检：是否只改了要求改的代码？是否有更简单的方案？是否碰到了不该碰的文件？

#### 2.7 代码质量

1. **DRY（不重复）**：发现重复代码就提取共用函数，只维护单一真相来源。
2. **命名即文档**：变量、函数、类名应揭示其用途，避免缩写；事件处理函数以 `handle` 开头。
3. **注释解释“为什么”而非“是什么”**：代码本身应自解释“是什么”，注释只写非显而易见的约束、Bug 规避和意外行为。
4. **方法实现必须有功能注释**：新增或修改的方法必须添加简洁的方法级注释，说明该方法完成什么功能；涉及非显而易见的约束、Bug 规避或副作用时一并说明原因。
5. **禁止在代码注释中引用任务、Issue 号或 PR 号**：这些属于提交信息，不随代码演进而腐烂。
6. **函数单一职责**：每个函数只做一件事；方法注释用于说明职责，不能代替拆分职责过多的方法。
7. **国际化语言必须同步完整**：新增、修改或删除国际化 key 时，必须在同一次变更中同步基础语言包和项目已支持的全部 locale 语言包；不得依赖基础语言包回退来代替目标语言翻译。
8. **国际化翻译必须真实有效**：各 locale 必须提供符合该语言的实际翻译，禁止复制中文、英文或使用占位文本。交付前必须确认本次涉及的 key 在每个语言包中恰好存在一次，并运行模块已有的语言包一致性测试。
9. **数据库约束必须写明用途和依赖点**：新增或修改 CHECK、UNIQUE、外键、默认值等数据库约束时，必须在该约束旁写明两件事——这条约束是做什么用的（拦掉哪类错误数据），以及什么地方依赖它（哪条查询、哪个流程、哪个唯一性假设靠它成立）。涉及 NULL、多列组合或阶段性范围限制（例如当前只允许部分用途）的约束尤其要写清楚，否则会被误当成漏写或被当成无用约束删掉；代码里依赖该约束保证结果的地方（如按唯一身份查询单行）也要在方法注释里写明由哪条约束保证。

## 三、工程文档语言

- Codex 新生成的设计文档、实施计划、集成说明和上游同步说明默认使用简体中文。
- 代码标识、命令、文件路径、API 路径和第三方项目原始名称保持原文，避免翻译造成歧义。

## 四、Git、数据与发布授权

- 每次改完代码**不要自动提交**，等用户明确说“提交”或“commit”后再执行。
- 用户说“提交”时，默认含义是依次完成 `git commit` 和 `git push`；用户只说“commit”时，只执行 `git commit`，不得擅自 `git push`。
- 用户明确要求“提交代码”或“提交”时，默认将当前工作区所有未提交代码（包括已跟踪和未跟踪文件）纳入同一笔提交。提交前必须使用 `git add -A`，并检查 `git status` 与 `git diff --cached --stat`，不得只选择部分功能文件或故意留下未提交改动，除非用户明确指定文件或范围。
- “提交”本身不包含打 tag、创建 GitHub Release、发布或部署；这些操作仍需用户另外明确要求。
- 保护用户已有改动；未经明确要求，不提交、不推送、不删除数据。
- **改完必审，发布必授权**：任何代码改动进入发布前必须先经过代码审查（含对抗验证），并修完审查发现的问题；审查通过也不等于可以发布——提交、打 tag、`prepare`、`publish`、部署等动作只在用户明确要求时执行，不得把“我已经把问题修好了”当作发布授权。

## 五、诊断、验证与回复

- 使用用户当前使用的语言，先给结论，回复保持简洁。
- 诊断时优先依据运行状态、日志、代码和配置，区分事实与推断。
- 对可能变化的信息先查询官方文档或当前运行状态。
- 优先修复根因；只能使用绕过方案时必须明确说明。
- 修改后运行与风险相匹配的测试；未验证不得声称完成。
- 最终回复只说明结果、验证情况和剩余风险，不复述完整过程。

## 六、完成前检查与禁止事项

### 6.1 开发完成检查

任务完成后，逐项确认：

1. ✅ 本次新增代码是否与仓库已有功能重复？是否存在可以改为调用现有能力的复制逻辑？
2. ✅ 公共层是否混入了渠道/业务独有逻辑？渠道模块是否包含本应复用的公共规则？
3. ✅ 新增页面/组件是否复用了现有公共组件、样式、主题？有没有创建平行的样式体系？
4. ✅ 新增的标识、主键、编号是否沿用了现有机制？
5. ✅ 是否有仅一个实现的抽象层？（有则标记为过度工程。）
6. ✅ 是否碰到了不该修改的文件？（有则回滚。）

**任一检查不满足时，任务不得标记为完成。**

### 6.2 禁止行为清单

以下行为在任何情况下禁止：

- ❌ 不检查就创建新组件、页面、服务或工具函数
- ❌ 复制现有代码后改名当作新实现
- ❌ 按设计文档或字段草图的字面命名新建同义字段、枚举或错误码（如已有 `created_at`/`updated_at`、`deleted_at` 时另造 `opened_at`/`closed_at`）
- ❌ 绕过现有抽象直接访问底层实现
- ❌ 删除现有公共代码后重新写一套
- ❌ 引入与现有架构冲突的新框架或依赖
- ❌ 对小改动重写整个文件
- ❌ 主动添加任务未要求的功能
- ❌ 修改与任务无关的代码
- ❌ 在代码注释中写“用于 XX 流程”“为 Issue #XX 添加”等任务引用
- ❌ 用硬编码样式绕过现有主题系统
- ❌ 提交未经验证的代码并声称“看起来没问题”
- ❌ 不确定时说“可能”或编造答案；应明确说明需要验证的事实
